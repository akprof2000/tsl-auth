Сборка на GitFlic на своих агентах

TSL Auth · gitflic.ru/project/uklad/tsl-auth · состояние на 04.10.2026 · исходник — docs/gitflic-runners.html в репозитории

GitFlic не даёт общих агентов: конвейер выполняют два наших агента на сервере сборки в Хельсинки. Каждый push в main собирает решение, гоняет все уровни тестов в docker:dind, сканирует образ и публикует образ и пакеты SDK в реестры GitFlic. Когда с сервера не проходит выгрузка в реестр, образ и пакеты публикуются с рабочей станции теми же командами.

3. Подготовка сервера

  1. Docker Engine и compose v2 на Linux-сервере с выходом в интернет. Входящие подключения агенту не нужны — он сам обращается к координатору GitFlic.
  2. Место. Задания с docker:dind оставляют анонимные тома с данными демона — до 100 ГБ в сутки. Нужен диск от 200 ГБ и регулярная очистка (см. раздел 12).
  3. Память. Заданию с .NET SDK и docker:dind нужно около 2 ГБ; сумму LIMIT_OF_CONCURRENCY_TO_PROCESS_JOBS по всем агентам подбирают по памяти сервера.
  4. Каталог агентов — ~/gitflic-runner: два compose-файла, скрипт очистки и его журнал.
  5. Чужие сервисы не трогать. На сервере живут uklad-gitflic-runner, агенты других проектов, YouTrack, plaudio, platform_dev. Никаких docker system prune -a, docker volume prune -a и удаления «всех» контейнеров.

4. Регистрация агентов

Агентов два: координатор выдаёт агенту примерно одно задание в минуту, поэтому два агента раздают задания вдвое быстрее одного. Оба на одном сервере, с одинаковыми тегами, каждый берёт до двух заданий одновременно.

4.1. Файл ~/gitflic-runner/docker-compose.yaml

services:
  runner:
    container_name: gitflic-runner-tsl-auth
    image: registry.gitflic.ru/company/gitflic/runner:latest
    environment:
      # URL со страницы «Агенты CI/CD», но с явным портом :443: без него агент 5.0.0 сохраняет порт «-1»
      # и падает при запросе конфигурации («Bad authority»).
      REG_URL: "https://coordinator.gitflic.ru:443/-/runner/registration"
      REG_TOKEN: "${GITFLIC_RUNNER_TOKEN}"     # токен — только из переменной окружения
      NAME: "tsl-auth-hel-1"
      TAGS: "tsl-auth,tsl-auth-hel"           # действует только при первой регистрации
      PRIVILEGED: "true"                      # нужно для сервиса docker:dind
      LOG_LEVEL: INFO
      CONCURRENCY_MODE: CUSTOM
      LIMIT_OF_CONCURRENCY_TO_PROCESS_JOBS: "2"
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
      - runner-config:/gitflic-runner/config
      - runner-log:/gitflic-runner/log
    restart: unless-stopped
volumes:
  runner-config:
  runner-log:

Второй агент — копия docker-compose-2.yaml с другими container_name (gitflic-runner-tsl-auth-2), NAME (tsl-auth-hel-2) и именами томов (runner2-config, runner2-log).

4.2. Запуск

cd ~/gitflic-runner
GITFLIC_RUNNER_TOKEN='<токен со страницы «Агенты CI/CD»>' docker compose -p gitflic-runner up -d
GITFLIC_RUNNER_TOKEN='<токен>' docker compose -p gitflic-runner-2 -f docker-compose-2.yaml up -d
  1. Агенты появляются в «Агенты CI/CD» проекта со статусом «активен». Проверка без браузера: ./scripts/gitflic.ps1 runners.
  2. Агент 5.0.0 регистрируется заново при каждом старте контейнера, поэтому токен регистрации не сбрасывайте, пока агенты могут перезапускаться. Если токен сбросили — перезапустите агентов с новым.
  3. Теги уже зарегистрированного агента меняются через GitFlic (агент → «Теги») или API (runner-tags); переменная TAGS при перезапуске их не меняет.
  4. Тег tsl-auth получают все задания конвейера; tsl-auth-hel — только проверка сети net-check-hel. Так когда-то разделяли сборку на рабочей станции и серверную проверку сети.
PRIVILEGED=true нужен только для docker:dind: задания идут в отдельных контейнерах и используют свой демон, а не Docker хоста. Поэтому агент проекта лучше держать на выделенной машине.

5. Конвейер gitflic-ci.yaml

6. Приёмы в заданиях

6.1. Сервис docker:dind

variables:
  DOCKER_HOST: tcp://docker:2375
  DOCKER_TLS_CERTDIR: ""
  TESTCONTAINERS_HOST_OVERRIDE: docker      # контейнеры тестов — по имени сервиса dind
  TESTCONTAINERS_RYUK_DISABLED: "true"

integration-tests:
  services:
    - name: docker:28-dind
      alias: docker
      command: ["--tls=false"]
  script:
    # dind стартует вместе с заданием — ждём демон до 60 с, иначе первая команда падает
    - for i in $(seq 1 60); do wget -q -O /dev/null http://docker:2375/_ping 2>/dev/null && break; sleep 1; done

6.2. Защита от «зелёного нуля»

dotnet test --no-build без бинарников или без найденных тестов завершается с кодом 0. После каждого запуска тестов — sh scripts/ci-check-trx.sh TestResults/unit.trx 100: требует, чтобы тесты выполнились (не меньше указанного числа) и ни один не упал.

6.3. Кэш NuGet

variables:
  NUGET_PACKAGES: $CI_PROJECT_DIR/.nuget/packages   # GitFlic кэширует только внутри каталога проекта
cache:
  key: nuget
  paths: [.nuget/packages/]

Задания без .NET указывают cache: [], чтобы не качать кэш зря.

6.4. Порядок через needs

Без явного needs GitFlic запускал publish-image, как только освобождался агент, — ещё до окончания тестов. Поэтому у публикации needs: [build-and-unit, integration-tests, sdk-contract, e2e-stand, build-image, scan-image]. Тестовые задания с needs: [build-and-unit] к тому же не тянут чужой image.tar (200 МБ): большие загрузки артефактов на агент обрывались.

6.5. Стенд в dind и socat

В e2e-stand сервис поднимается docker compose внутри dind, а браузер и скрипты задания ходят на localhost. Порты сводит socat:

for p in $(seq 8080 8099); do socat TCP-LISTEN:$p,fork,reuseaddr TCP:docker:$p & done

Кластер, стенд мониторинга, OpenBao и секреты из файла настроек здесь не проверяются: их compose монтирует каталоги репозитория, которых нет на хосте dind. Это ручная проверка перед релизом (tests/resilience/run-*.ps1).

6.6. Секреты стенда в CI

Пароль администратора и секрет клиента admin-cli генерируются на каждый прогон из /dev/urandom и живут только внутри задания.

8. Версии и публикация

  • Версия прогона main: MAJOR.MINOR из файла sdk/VERSION плюс unix-время коммита — например 1.6.1790990000. Порядковый номер не годится: CI_PIPELINE_ID — UUID, а число коммитов при неглубоком клоне постоянно.
  • Образ: crane push image.tar …:sha-<коммит>, затем crane tag версии прогона и latest (на теге — ещё X.Y.Z). Используется crane в alpine, а не docker push: демон dind не дожидался ответа реестра, а crane грузит архив напрямую.
  • NuGet — прямой PUT (scripts/gitflic-nuget-push.sh): dotnet nuget push добавляет «/» к адресу и получает 404. AssemblyVersion не больше 65535, поэтому время коммита — только в PackageVersion.
  • npm — .npmrc с _authToken; npm не публикует версию «меньше» уже существующей — временную большую версию сначала удаляют.
  • PyPI — twine через .pypirc (scripts/gitflic-pypirc.sh), без --skip-existing (реестр его не поддерживает).
  • Maven — mvn deploy -DaltDeploymentRepository=gitflic::$PKG_BASE/maven, учётные данные в ~/.m2/settings.xml, созданном в задании.
  • Go — сам репозиторий (sdk/go), публиковать нечего.
С 30.09.2026 с сервера обрывается выгрузка в registry.gitflic.ru. net-check-hel даёт WARNING, publish-image падает на тайм-аутах PATCH blob, хотя все тесты зелёные. Сборку и тесты это не затрагивает. Образ и пакеты выпуска публикуются с рабочей станции (раздел 10). Когда net-check-hel снова станет зелёным, публикация вернётся на агента сама.

9. Выпуск релиза

GitFlic не создаёт конвейер на push тега, а POST …/cicd/pipeline/start с {"ref":"vX.Y.Z"} запускает обычный прогон main. Поэтому релиз оформляется вручную через API (образец — релиз 1.5.1):

  1. Дождаться зелёного main: все задания, кроме публикации.
  2. Поставить аннотированный тег и отправить его: git tag -a vX.Y.Z -m "…", git push origin vX.Y.Z.
  3. Опубликовать образ с тегами X.Y.Z, X.Y, X, latest и пакеты SDK версией X.Y.Z — с агента или с рабочей станции. Временные версии X.Y.<время> удалить.
  4. Собрать файлы релиза — только архивы (текстовые файлы GitFlic отвергает с 415): tsl-auth-image-X.Y.Z-linux-amd64.tar.gz (docker save | gzip), tsl-auth-sdk-X.Y.Z.tar.gz (scripts/build-sdk-packages.sh X.Y.Z), tsl-auth-deploy-X.Y.Z.tar.gz (compose, .env.example, deploy/, демо- и импорт-скрипты), tsl-auth-docs-X.Y.Z.zip.
  5. Создать релиз: POST /project/uklad/tsl-auth/release с JSON {title, tagName, description, isDraft, isPreRelease} (другие имена полей — 500). SHA-256 файлов — в описании.
  6. Загрузить файлы: POST …/release/<id>/file, multipart-поле files. Удалить неудачный релиз — DELETE …/release/<id>.
  7. Обновить затронутые статьи YouTrack (ЧТЗ и Word-вложения).
scripts/gitflic-prune.sh с KEEP=1 для образа не запускать: теги 1, 1.5, 1.5.1, latest он считает разными версиями и удалил бы нужные.

10. Публикация с рабочей станции

Когда агент не может выгрузить образ, используются те же команды, что в заданиях. Вход — логин GITFLIC_API_USER, пароль — транспортный токен; вводятся интерактивно или из файла токенов, не в командной строке.

docker login registry.gitflic.ru
docker build -t registry.gitflic.ru/project/uklad/tsl-auth/tsl-auth:X.Y.Z .
for t in X.Y X latest sha-<коммит>; do
  docker tag registry.gitflic.ru/project/uklad/tsl-auth/tsl-auth:X.Y.Z registry.gitflic.ru/project/uklad/tsl-auth/tsl-auth:$t
done
docker push --all-tags registry.gitflic.ru/project/uklad/tsl-auth/tsl-auth

Пакеты SDK — командами из заданий publish-sdk-* с PKG_BASE=https://registry.gitflic.ru/project/uklad/tsl-auth/package/- и GITFLIC_PKG_USER/GITFLIC_PKG_TOKEN в окружении.

11. Зеркало GitHub и Git LFS

  • git push origin main отправляет в оба репозитория: у origin два push-URL (GitFlic и GitHub).
  • *.docx хранятся в Git LFS. Без настройки ниже git-lfs шлёт объекты на последний push-URL (GitHub), и в GitFlic остаются указатели без содержимого (404 при скачивании). Проверку блокировок GitFlic отвергает (403): 
    git config remote.origin.lfsurl https://gitflic.ru/project/uklad/tsl-auth.git/info/lfs
git config remote.origin.lfspushurl https://gitflic.ru/project/uklad/tsl-auth.git/info/lfs
git config lfs.https://gitflic.ru/project/uklad/tsl-auth.git/info/lfs.locksverify false
  • Если коммит меняет *.docx, GitHub отклоняет push («pre-receive hook declined»). Поэтому перед push: git lfs push https://github.com/akprof2000/tsl-auth.git main.
  • Задание mirror-github (scripts/mirror-github.sh) дотягивает историю (--unshallow), переносит объекты LFS текущего коммита (git lfs fetch → git lfs push; у git-lfs в Alpine нет --quiet), затем main и теги.
  • Проверка LFS: чистый клон GitFlic и git lfs pull — файлы полного размера, а не указатели по 130 байт.

12. Обслуживание

12.1. Место на сервере

Cron пользователя каждые 3 часа запускает ~/gitflic-runner/hel-cleanup.sh (копия scripts/hel-cleanup.sh). Он удаляет только анонимные висячие тома — пустые или с данными dind (overlay2, containers, image) — и образы без тега старше суток. Именованные тома чужих сервисов не трогает.

scp -P 443 scripts/hel-cleanup.sh alexey_kozlov@77.42.83.24:~/gitflic-runner/
ssh -p 443 alexey_kozlov@77.42.83.24 '(crontab -l 2>/dev/null | grep -v hel-cleanup; echo "17 */3 * * * sh $HOME/gitflic-runner/hel-cleanup.sh >> $HOME/gitflic-runner/hel-cleanup.log 2>&1") | crontab -'
ssh -p 443 alexey_kozlov@77.42.83.24 'df -h /; docker system df; sh ~/gitflic-runner/hel-cleanup.sh'

После своих заданий и выпусков — проверить df -h /. Без очистки 30.09.2026 задания падали с «No space left on device».

12.2. Место на GitFlic

  • Артефакты заданий живут от 2 часов до суток (expire_in). GitFlic сам их не удаляет — их убирает удаление старых конвейеров: ./scripts/gitflic.ps1 prune-pipelines -Keep 3.
  • В реестрах и релизах — не больше трёх версий (задание cleanup), а после выпуска — только текущий выпуск (X.Y.Z + latest) и последняя версия пакетов.

12.3. Обновление агента

cd ~/gitflic-runner
docker compose -p gitflic-runner pull
GITFLIC_RUNNER_TOKEN='<токен>' docker compose -p gitflic-runner up -d

13. GitFlic без браузера

scripts/gitflic.ps1 берёт GITFLIC_API_TOKEN из файла токенов и ходит в https://api.gitflic.ru:

./scripts/gitflic.ps1 pipelines -Top 5          # конвейеры
./scripts/gitflic.ps1 jobs 72                   # задания конвейера
./scripts/gitflic.ps1 runners                   # агенты и их теги
./scripts/gitflic.ps1 prune-pipelines -Keep 3   # удалить старые конвейеры вместе с артефактами
./scripts/gitflic.ps1 raw GET /project/uklad/tsl-auth/cicd/job/347/artifacts
  • Журнал задания — артефакт с fileType: trace: скачать по downloadUrl с заголовком Authorization: token ….
  • Запуск конвейера: POST /project/uklad/tsl-auth/cicd/pipeline/start с телом {"ref":"main"}.
  • git по HTTPS: git config credential.https://gitflic.ru.helper '!sh scripts/git-credential-gitflic.sh'.

16. Чек-лист нового проекта

  • Проект на GitFlic создан, origin → GitFlic, второй push-URL → GitHub (зеркало), настройки LFS из раздела 11.
  • Два агента зарегистрированы с тегом проекта, PRIVILEGED=true, REG_URL с :443.
  • Cron очистки томов dind на сервере работает, места больше 100 ГБ.
  • gitflic-ci.yaml: workflow.rules (main и v*), кэш пакетов в каталоге проекта, dind с ожиданием _ping.
  • После каждого прогона тестов — проверка результатов (ci-check-trx.sh или аналог).
  • Публикация — с needs на все проверки, образ через crane, версия = sdk/VERSION + время коммита.
  • Переменные проекта: GITFLIC_PKG_USER/TOKEN, GITFLIC_API_TOKEN, GITHUB_MIRROR_TOKEN.
  • Задание cleanup (не больше трёх версий) и периодический prune-pipelines.
  • Задание проверки сети (net-check), чтобы видеть, когда публикацию с агента можно вернуть.
  • Порядок выпуска (раздел 9) и ручной публикации (раздел 10) записан в CLAUDE.md проекта.

Подробности и история решений — docs/gitflic-ci.md, gitflic-ci.yaml (комментарии к заданиям) и раздел «Репозитории и CI» в CLAUDE.md.
