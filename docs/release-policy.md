# Релизная политика

Правила, по которым выпускаются версии TSL Auth. Механику (сборка образа, подпись, публикация) выполняет CI;
здесь — что считается релизом, когда его выпускать и что при этом обязательно.

## Версии

Версии — [семантические](https://semver.org/lang/ru/): `MAJOR.MINOR.PATCH`, тег в git — `vX.Y.Z`.

| Часть | Когда увеличивается | Примеры |
|---|---|---|
| MAJOR | Несовместимое изменение: удалён или переименован параметр настройки, изменился формат токена или API, требуется ручная миграция данных | смена формата claims; удаление `Observability__Loki__*` без переходного периода |
| MINOR | Новая возможность или заметное изменение поведения, совместимое с прежними настройками и данными | двухфакторный вход, стенд Victoria, конвейер GitFlic |
| PATCH | Исправление без новых возможностей: ошибка, безопасность, документация, зависимости | обход бага агента GitFlic, обновление базового образа |

Схема БД обновляется автоматически при старте, поэтому новая миграция сама по себе не делает версию MAJOR.
MAJOR нужен, если старая версия сервиса не сможет работать с новой схемой **и** откат требует ручных действий.

До версии 1.0 было допустимо менять всё; с 1.0 действует таблица выше.

## Ветки и коммиты

- Разработка идёт в `main`; отдельных веток и pull request'ов нет (см. память проекта: коммит сразу в main).
- Основной репозиторий — GitFlic (`gitflic.ru/project/uklad/tsl-auth`), GitHub — зеркало исходников (`scripts/mirror-github.sh`).
- Каждый коммит проходит конвейер GitFlic (`gitflic-ci.yaml`): сборка, unit и интеграционные тесты, документация,
  контрактные тесты SDK, E2E-стенд, Trivy, публикация образа и пакетов. Красный конвейер на `main` чинится следующим
  коммитом, а не откатом.
- Релиз ставится только на коммит с зелёным конвейером GitFlic. Кластер, стенд мониторинга, OpenBao и секреты из файла
  настроек проверяются перед релизом вручную скриптами `tests/resilience/run-*.ps1` (в конвейер они не входят).

## Что входит в релиз

1. Тег `vX.Y.Z` на `main` в GitFlic. Конвейер собирает образ, сканирует его (Trivy) и публикует в реестр GitFlic
   с тегами `X.Y.Z`, версией GitFlic и `latest`; пакеты SDK — в реестр пакетов проекта.
2. Релиз GitFlic с заметками (создаётся конвейером по тегу): «Главное», «Несовместимые изменения»
   (что нужно сделать при обновлении), «Документация», «Образ».
3. Документация соответствует версии: `docs/*.md`, ЧТЗ (`docs/tz.md` и Word), руководство пользователя.
   Расхождение документации и поведения считается дефектом и блокирует релиз.
4. Клиентские библиотеки: конвейер собирает NuGet, npm, PyPI и Maven и публикует их в реестр пакетов проекта GitFlic;
   модуль Go берётся из репозитория (`sdk/go`). Изменение контракта SDK (`docs/client-contract.md`) — MINOR при
   расширении, MAJOR при удалении или переименовании полей и кодов.
5. GitHub получает исходники и теги зеркалом; сборки, образы и релизы там больше не выпускаются (последний — v1.4.1).
6. GitFlic версионируется независимо: `MAJOR.MINOR` из `sdk/VERSION` плюс unix-время коммита (например `1.4.1790700000`),
   образ и пакеты каждого прогона `main`; вся сборка и публикация на GitFlic идут на его агентах. При смене MAJOR или MINOR обновляется и `sdk/VERSION`.

## Что блокирует релиз

- Красный конвейер GitFlic на релизном коммите. Ложные падения (медленный раннер, обрыв Chromium в mermaid-cli) — перезапуск
  задания; если падение повторяется, релиза нет до разбора.
- Критическая или высокая уязвимость с исправлением в образе (Trivy) — исправляется или оформляется принятие риска
  в заметках о выпуске с датой пересмотра.
- Литеральные секреты в репозитории (gitleaks).
- Незакрытое несовместимое изменение без описания обновления в заметках.

## Обновление и откат у заказчика

- Обновление — смена тега образа и перезапуск (в кластере — поочерёдно). Схема обновляется при старте под advisory-lock.
- Откат на предыдущую версию — смена тега обратно; запуск на схеме новее версии сервиса запрещён без
  `Database__AllowDowngrade=true`. Для релиза с необратимой миграцией заметки содержат отдельный план отката.
- Закрытый контур: образ переносится `scripts/export-images.ps1` вместе с compose и `.env.example` той же версии.

## Периодичность

Фиксированного календаря нет. MINOR выпускается по завершении функционального блока ЧТЗ или решения заказчика;
PATCH — по мере исправлений, без накопления. Несколько исправлений подряд можно объединить в один PATCH, если
между ними не было релиза.

## Кто и как выпускает

Релиз делает тот, кто довёл изменения до зелёного CI и E2E:

```bash
git tag -a vX.Y.Z <коммит> -m "vX.Y.Z: коротко о главном"
```

```bash
git push origin vX.Y.Z
```

Ход публикации виден в конвейере GitFlic по тегу (в том числе без браузера: `scripts/gitflic.ps1 pipelines`).
