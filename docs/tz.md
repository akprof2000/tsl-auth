## 1. Назначение и границы

TSL Auth выполняет единую идентификацию и аутентификацию пользователей и технических клиентов ERP по OAuth 2.0 / OpenID Connect. Сервис хранит учётные записи, роли приложений, матрицы «роль × разрешение» и выдаёт подписанные токены. Прикладные системы проверяют токен локально и не хранят паролей.

| Параметр | Значение |
|---|---|
| Место в архитектуре ERP | Компонент «Управление идентификацией» (04.02); в базовой архитектуре ТСЛ — «Авторизатор» |
| Исходный код | https://gitflic.ru/project/uklad/tsl-auth (основной репозиторий, сборка и реестры); зеркало — https://github.com/akprof2000/tsl-auth; лицензия MIT |
| Поставка | Docker-образ `akprof2000/tsl-auth` (Docker Hub, GHCR), подписанный cosign |
| Технологии | .NET 10, ASP.NET Core, OpenIddict 7, ASP.NET Core Identity, EF Core; SQLite или PostgreSQL 14+ |
| Очередь | Первая: вход пользователей ERP, технические клиенты Flowable, обработчиков обмена, DWH и импорта из 1С |

Принятое решение. Граница ответственности:

| Входит в tsl-auth | Не входит в tsl-auth |
|---|---|
| Учётные записи, пароли, блокировка, двухфакторный вход, выход, сессии | Организационная и финансовая иерархия (ядро ERP) |
| Роли и разрешения на уровне операций приложения | Области доступа по организациям, подразделениям, ЦФО, проектам и объектам: применяются ядром ERP при выборке данных |
| Токены для пользователей и технических клиентов | Маскирование чувствительных полей в формах и отчётах ERP |
| Журнал безопасности входов, учётных записей и назначений | Аудит бизнес-действий с документами ERP (04.15, ядро ERP) |

Принятое решение (В-1): области доступа хранятся в отдельной базе ядра ERP рядом с оргструктурой; tsl-auth их не хранит и в токене не передаёт.

## 3. Процессы и сценарии

Основные сценарии:

1. Вход пользователя в приложение ERP по authorization code + PKCE.
2. Вызов API сервиса другим сервисом: client credentials; вызов от имени пользователя — token exchange.
3. Создание учётной записи администратором: с паролем, временным паролем или приглашением.
4. Саморегистрация с заявкой на роль; заявку одобряет администратор, приложение или бот.
5. Сброс пароля по email или через бота.
6. Блокировка учётной записи офицером безопасности через бота.
7. Прекращение доступа при увольнении или смене роли.
8. Двухфакторный вход: пароль → код с почты или из мессенджера (для ролей с флагом 2FA).
9. Автоматическое отключение учётной записи без входа 90 дней (кроме администраторов сервиса).
10. Подчинённые клиенты: сервис-владелец (например, Import API) по команде оператора заводит технического клиента
    агента через App API в рамках политики администратора; агент входит по ключу (`private_key_jwt`), а не по секрету;
    отключение агента действует на выдачу токенов во всех сервисах.

## 6. Функциональные требования

### 6.1. Протоколы и токены

| № | Требование | Статус |
|---|---|---|
| Ф-1 | Сервис выполняет OAuth 2.0 / OIDC: authorization code + PKCE (S256 обязателен), client credentials, refresh с ротацией, token exchange (RFC 8693), introspection, revocation, userinfo, logout, discovery, JWKS. Grant password оставлен для унаследованных клиентов и включается для приложения отдельно | есть |
| Ф-2 | Access-токен — JWT RS256. Claims `role`, `permissions` (`<client_id>:<разрешение>`) и `resource_access` совместимы с Keycloak | есть |
| Ф-3 | Сроки жизни задаются глобально и для приложения; клиент может их только сократить. По умолчанию: access и id — 15 мин, refresh — 14 дней, код авторизации — 5 мин, абсолютный срок сессии — 90 дней | есть |
| Ф-4 | Изменение прав применяется со следующего refresh, не позднее срока жизни access-токена. Отзыв сессии действует на всех узлах сразу | есть |
| Ф-5 | Персональный токен доступа (PAT) для скриптов не превышает текущих прав владельца и отзывается вместе с отключением учётной записи | есть |

### 6.2. Роли и полномочия (03.01, 04.09)

| № | Требование | Статус |
|---|---|---|
| Ф-6 | У каждого приложения есть разрешения на уровне операций (ввод, просмотр, проведение, формирование отчётов, удаление), роли и матрица «роль × разрешение». Роль имеет техническое имя для токена и название для людей | есть |
| Ф-7 | Роли назначаются пользователям и техническим клиентам. Одна учётная запись имеет роли в нескольких приложениях; итоговые разрешения — объединение разрешений ролей | есть |
| Ф-8 | Роль помечается как запрашиваемая: пользователь запрашивает её при регистрации или заявкой; назначение выполняется только после одобрения | есть |
| Ф-9 | Назначение роли имеет период действия (с, по). По окончании периода сервис снимает роль, отзывает refresh-токены и пишет событие в журнал | 1-я очередь |
| Ф-10 | Несовместимые роли не проверяются: доступ задаётся матрицей «роль × разрешение» приложения, пары несовместимых ролей заказчиком не определены (решение В-8) | не требуется |
| Ф-11 | Замещение назначает только администратор доступа: пользователь получает роли другого пользователя на указанный период. В токене замещающего передаётся claim с идентификатором замещаемого. По окончании периода роли снимаются | 1-я очередь |
| Ф-12 | Учётная запись без входа дольше 90 дней отключается автоматически при плановом обслуживании БД (раз в час); срок и включение меняются в настройках («Неактивные учётные записи»). Для никогда не входивших отсчёт идёт от даты создания. Пользователи с ролью `administrator` сервиса автоматически не отключаются — только вручную. Отключение отзывает сессии, пишется в журнал (`user.disabled_inactive`) и уходит в ленту `security.alert`. Отчёт для пересмотра прав с выгрузкой в CSV — 1-я очередь | есть (отключение); 1-я очередь (отчёт) |
| Ф-13 | Роли `tsl-auth-admin` отделены от ролей приложений ERP. Технический администратор сервиса не получает доступа к бизнес-данным ERP через tsl-auth | есть |

### 6.3. Учётные записи и аутентификация

| № | Требование | Статус |
|---|---|---|
| Ф-14 | Администратор создаёт пользователя с паролем, временным паролем (смена при первом входе) или ссылкой-приглашением | есть |
| Ф-15 | Пользователь сбрасывает пароль по email или через бота мессенджера и меняет пароль в личном кабинете | есть |
| Ф-16 | Политика паролей: длина, классы символов, запрет логина в пароле, история, срок действия. После N неудачных попыток учётная запись временно блокируется | есть |
| Ф-17 | Саморегистрация в приложении с заявкой на роли | есть |
| Ф-18 | Двухфакторный вход назначается ролям: администратор ставит у роли флаг «требовать 2FA» в матрице приложения или через Admin API (`PUT /api/admin/applications/{client}/roles/{role}/two-factor`); приложение через App API флаг не меняет. Если у пользователя есть хотя бы одна такая роль, после пароля открывается страница кода. Каналы: код на email (кнопка «Отправить код») и код в мессенджере (пользователь пишет боту `/code`, бот получает код по Bot API `POST /api/bot/2fa-code`). Коды одноразовые, по времени (TOTP по security stamp), не хранятся и действуют несколько минут; неверные коды считаются в блокировку. Нет ни email, ни мессенджера — вход не выполняется, пользователь видит причину. Password grant для таких пользователей закрыт. Сессия, полученная без кода, после назначения роли не продлевается. В токенах передаётся claim `amr` (`pwd` или `pwd`, `otp`, `mfa`). TOTP-приложения и аппаратные ключи — задел на будущее; повторное подтверждение критических операций — на стороне прикладной системы (решения В-7, В-9) | есть |
| Ф-19 | Прекращение доступа работает как отзыв refresh-токена: отключение учётной записи или снятие роли применяется при следующем refresh, не позднее срока жизни access-токена (15 мин). Отключение вызывает администратор или ERP через Admin API (решение В-3) | есть |

Контрактные тесты против живого сервиса в CI; пакеты выпускаются вместе с сервисом и переносятся в закрытый контур | есть |
| Ф-28 | Подчинённые клиенты (РС-16 проекта 1c-import): приложение-владелец через App API `/api/app/clients` заводит, меняет ключи, отключает и удаляет своих технических клиентов в рамках политики администратора (префикс `client_id`, белый список своих ролей, только `client_credentials`, способы входа, предел числа, срок токена, предел неактивности). Изменения — только делегированным токеном оператора (token exchange, `act.sub` = владелец) с разрешением политики в матрице владельца; сервисный токен — только чтение (в тестовых стендах — и изменения); клиентский токен, полученный обменом другим приложением, владельцем не считается; без самоуправления владельца доступа нет. Предел неактивности считается по отметке последнего выданного токена. Чужой клиент — 404; `tsl-auth-admin`, `tsl-auth-app`, чужие роли и потоки недоступны ни одним API. Каждое действие — в журнале безопасности с оператором и владельцем; метрика числа подчинённых по владельцам | есть |
| Ф-29 | Вход клиента по ключу `private_key_jwt` (RFC 7523): ключ хранится как открытый JWK EC P-256 (`kid` — отпечаток RFC 7638, до двух ключей для плавной смены), assertion только ES256, `iss = sub = client_id`, `aud` — issuer сервиса (как в discovery), `exp − iat` ≤ 5 мин, `iat`/`nbf`/`exp` — секунды, `jti` одноразовый для всего кластера; `alg=none`/`HS*` отклоняются; клиенту — только `invalid_client` на token, introspection и revocation, причина — в журнал (warning) и метрику; discovery публикует `private_key_jwt` и `ES256`. SDK .NET и Go входят по ключу; предел отказов по паре «`client_id` + IP» | есть |
| Ф-30 | Отключение клиента (`tsl_disabled`): администратор — любого, владелец — подчинённого; `invalid_client` на token и authorize, отзыв сессий и токенов (introspection `active=false`), события `application.disabled` / `application.enabled` / `application.deleted` с `client_id` и владельцем | есть |

## 7. Проверки и ограничения

- Сервис отклоняет запрос без PKCE S256 для public-клиента.
- Сервис не выдаёт токен отключённой, заблокированной или ожидающей роли учётной записи.
- Клиент не получает scope и разрешения сверх назначенных ему ролей; token exchange не расширяет права пользователя.
- Приложение через App API не видит и не меняет данные другого приложения.
- Бот не выполняет действие над чужой учётной записью без роли `security-officer` у привязанного отправителя.
- Rate limiting ограничивает вход, `/connect/token`, introspect и revoke.

## 8. Интеграции

| Потребитель | Способ | Идентификация |
|---|---|---|
| UI ERP (React) | authorization code + PKCE, refresh с ротацией | public-клиент |
| Операционное ядро ERP (FastAPI) | Проверка JWT по JWKS: подпись RS256, `iss`, `aud`, `exp`, права по claim `permissions` | resource server |
| Flowable, обработчики RabbitMQ, Airflow/DWH, импорт из 1С | client credentials; вызов от имени пользователя — token exchange | confidential-клиенты |
| Ядро ERP (кадровые события, отчёт пересмотра прав) | Admin API, лента событий | confidential-клиент `admin-cli` |
| Боты мессенджеров | Bot API | confidential-клиент с ролью `security-bot` |

Контракт токена версионируется: состав claims меняется с обратной совместимостью либо с переходным периодом, как требует 04.12. В репозитории есть примеры интеграции на .NET, Node.js, Go, Python и Java и демо «Документооборот»: PWA, App API и бот. Пример для Python/FastAPI входит в первую очередь.

Подключение потребителей выполняется клиентскими библиотеками (`sdk/`): NuGet `TslAuth.Client`, npm `@tsl/auth-client`
(сервер и браузер), модуль Go, PyPI `tsl-auth-client`, Maven `ru.tsl.auth:tsl-auth-client`. Все пять реализуют один
контракт (`docs/client-contract.md`): порядок проверок, коды ошибок, чтение `permissions`, кэш JWKS, ротация refresh —
и проверяются контрактными тестами против живого контейнера. Пакеты версионируются вместе с сервисом и публикуются
в реестры пакетов GitHub и GitFlic; в закрытый контур переносятся вместе с образами.

## 9. Права доступа

- Минимальные полномочия: технический клиент получает только разрешения, нужные его операциям.
- Административные интерфейсы tsl-auth (админка, Admin API) доступны только ролям `tsl-auth-admin`; аудитор имеет права только на просмотр.
- Доступ к журналу безопасности выдаётся отдельной ролью и сам журналируется (1-я очередь).
- Аварийный доступ: CLI восстановления администратора запускается только из контейнера сервиса; запуск пишется в журнал.

Сервис не хранит состояния в памяти: ключи подписи, сессии, настройки и очереди находятся в БД, поэтому любой узел кластера обслуживает любой запрос. В работе нет обращений в интернет; интерфейс и справочник API работают без CDN. Сервис — отдельный компонент, а не модуль монолита ERP: ERP зависит только от стандартного OIDC-контракта, поэтому замена поставщика не меняет бизнес-логику (04.02, 04.14).

### 11.2. Производительность (04.05)

Для расчёта принимается верхняя граница первой очереди — 220 активных пользователей ERP одновременно.

| Показатель | Одиночный режим (SQLite) | Кластер (3 узла + PostgreSQL) |
|---|---|---|
| Пропускная способность | не менее 400 запросов/с | не менее 600 запросов/с |
| client_credentials, p95 | до 2,5 с | до 200 мс |
| Вход по паролю (PBKDF2 100 000 итераций), p95 | до 5 с | до 700 мс |
| Ошибки под нагрузкой | 0 % | 0 % |

Промышленный режим ERP — кластер: вход укладывается в 2 с для 95 % запросов, как требует 04.05 для типовой операции. Методика: k6, 45 виртуальных пользователей, 60 с (`tests/load`). В первой очереди профиль нагрузки дополняется сценарием 220 пользователей.

### 11.4. Резервное копирование и восстановление (04.08)

Копируются БД сервиса (учётные записи, роли, клиенты, ключи подписи, журнал) и мастер-ключ; без мастер-ключа зашифрованные поля не восстанавливаются, поэтому мастер-ключ хранится отдельно от копий БД.

| № | Требование | Статус |
|---|---|---|
| К-1 | Режим копирования PostgreSQL — по 04.08: полная копия еженедельно, ежедневная инкрементальная, журналы транзакций с интервалом не более 15 минут; суточные копии хранятся 35 дней, недельные — 6 месяцев. Мастер-ключ в промышленной среде хранится в OpenBao отдельно от копий БД (решение В-6) | 1-я очередь |
| К-2 | Перед пересборкой схемы сервис сам делает резервную копию БД | есть |
| К-3 | Восстановление проверяется раз в квартал в изолированной среде: данные, права, вход пользователей и технических клиентов. Результат оформляется протоколом | 1-я очередь |

### 11.7. Мониторинг и эксплуатация (04.10)

Сервис отдаёт `/health/live` и `/health/ready`, метрики в формате Prometheus (`/metrics`, их опрашивает VictoriaMetrics), трассировки по OTLP (через коллектор в VictoriaTraces), журналы в stdout (их собирает Vector в VictoriaLogs). Метрики: число входов и отказов, выдача токенов по grant type, блокировки, очередь вебхуков, время ответа. Идентификатор трассировки связывает запрос и журнал приложения; с событием журнала безопасности — после А-2а. Пороги уведомлений и ответственные — по решению A17 архитектурного ЧТЗ.

### 11.8. Среды (04.11)

Среды разработки, тестирования и промышленной эксплуатации используют отдельные экземпляры tsl-auth с отдельными БД, мастер-ключами, секретами клиентов и `Auth__Issuer`. Токен одной среды не принимается в другой. Автотесты создают учётные записи и секреты при запуске и не используют продуктивных данных.

## 13. Миграция данных

Переход с другого поставщика: формат claims совместим с Keycloak, поэтому проверка прав в приложениях не переписывается. Учётные записи создаются через Admin API; пароли не переносятся — пользователи получают приглашение или временный пароль. Перенос одиночного режима в кластер выполняет CLI `migrate-to-postgres`.

## 18. Принятые решения по вопросам

Ответы заказчика на [вопросы для ЧТЗ](tz-questions.md).

| № | Вопрос | Решение |
|---|---|---|
| В-1 | Где хранятся области доступа | В отдельной базе ядра ERP рядом с оргструктурой. tsl-auth их не хранит |
| В-2 | Делегирование и замещение | Замещение назначает администратор доступа (Ф-11) |
| В-3 | Прекращение доступа при увольнении | Как отзыв refresh-токена: применяется при следующем refresh, не позднее 15 минут (Ф-19) |
| В-4 | Срок развёртывания OpenBao | На MVP секреты хранятся в `.env` и файле настроек |
| В-5 | Сроки хранения журнала | По умолчанию: входы — 1 год, изменения и действия администраторов — 5 лет, технические события — 90 дней (А-4, реализовано) |
| В-6 | Резервное копирование и мастер-ключ | В промышленной среде мастер-ключ и секреты — в OpenBao, отдельно от копий БД (К-1) |
| В-7 | Критические операции с повторным подтверждением | Не относится к tsl-auth: определяется прикладной системой, например документооборотом. tsl-auth передаёт claim `amr` |
| В-8 | Несовместимые роли | Не требуются: доступ задаётся матрицей «роль × разрешение» (Ф-10) |
| В-9 | Способ второго фактора | Код на email и в мессенджер через бота; какие роли требуют второй фактор, задаёт администратор флагом роли. TOTP и аппаратные ключи — задел на будущее (Ф-18, реализовано) |
| В-10 | Отключение неактивных учётных записей | Автоматически после 90 дней без входа, кроме администраторов сервиса — их отключают только вручную (Ф-12, реализовано) |
| В-11 | Привязка токена подчинённого клиента к ключу (DPoP, RFC 9449; постановка `task-managed-clients.md`, этап 2) | Отложено: OpenIddict 7.7 не поддерживает DPoP. Пока риск кражи access-токена ограничен сроком 5 минут и отключением клиента; вернуться при появлении поддержки в OpenIddict или переходе на mTLS (RFC 8705) |

Остаются открытыми: частота пересмотра прав и ответственные за него; срок, после которого отключённая учётная запись удаляется.
